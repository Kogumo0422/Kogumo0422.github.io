# fuzzing과 fuzzer 개요

### **1. fuzzing**이란?

fuzzing은 다양한 입력을 테스트 대상에 반복적으로 전달하고 실행 결과를 관찰해 버그를 찾는 테스트 기법이다.

발견된 오류는 이후 재현하고 원인을 분석한다.

예를 들어 PNG 처리 프로그램을 fuzzing한다면, 정상 PNG 파일을 시드로 준비하고 fuzzer가 이를 변형해 프로그램에 전달한다. 

충돌이 발생하면 해당 입력을 저장해 다시 실행하고, 충돌 원인이 실제 버그나 보안 취약점인지 분석한다.


### 1-1. fuzzing의 기본 동작 과정

fuzzing은 일반적으로 다음 과정으로 이루어진다.

1. 정상적인 입력이나 입력 형식을 준비한다.
2. fuzzer가 입력을 생성하거나 변형한다.
3. 생성된 입력을 대상 프로그램에 전달한다.
4. 프로그램의 실행 상태를 관찰한다.
5. 비정상 종료, 메모리 오류, 무한 반복 등을 발견한다.
6. 문제를 발생시킨 입력을 저장하고 분석한다.

fuzzer가 주로 탐지하는 현상은 다음과 같다.

- 프로그램 충돌(Crash)
- 버퍼 오버플로
- Use-After-Free
- 정수 오버플로
- 메모리 누수
- 예외 처리 실패
- 무한 반복과 시간 초과
- 비정상적으로 많은 CPU·메모리 사용
- 논리적 오류
- 보안 검증 우회

단순히 프로그램이 종료됐다고 해서 모두 취약점인 것은 아니다. 

저장된 입력을 다시 실행해 보고, 디버거와 메모리 검사 도구 등을 이용해 원인을 확인해야 한다.

### **2. fuzzer**란?

fuzzer는 테스트 대상에 넣을 입력을 자동으로 생성하거나 변형하고, 이를 반복적으로 전달하는 도구이다.

fuzzer에 따라 프로그램의 충돌 여부나 코드 실행 범위를 관찰하고, 다음 테스트에 유용한 입력을 골라 보관하기도 한다.

입력의 형태는 대상에 따라 달라진다.

| 테스트 대상 | fuzzer가 전달하는 입력 |
| --- | --- |
| 이미지 뷰어 | 변형한 PNG 파일 |
| 웹 서버 | 변형한 HTTP 요청 |
| 라이브러리 함수 | 함수에 전달할 바이트 데이터 |
| 명령행 프로그램 | 표준 입력 또는 실행 인자 |

### 3. fuzzer의 주요 종류

fuzzer는 입력 생성 방식, 프로그램 내부 정보의 활용 정도, 실행 방식 등에 따라 분류할 수 있다.

#### **3-1. 입력 생성 방식에 따른 분류**

**⓵ 생성 기반 fuzzer**

입력 형식이나 문법을 바탕으로 새로운 입력을 처음부터 생성한다.

예를 들어 HTTP 요청의 구조를 알고 있다면 다음과 같은 요소를 조합해 새로운 요청을 만든다.

```jsx
METHOD /PATH HTTP/1.1
Header: Value
```

특징:

- 복잡한 입력 형식을 다루기 좋다.
- 정상적인 구조를 유지하는 입력을 만들 수 있다.
- 입력 규칙이나 프로토콜에 대한 사전 지식이 필요하다.
- 파서, 컴파일러, 네트워크 프로토콜 테스트에 유리하다.

**⓶ 변이 기반 fuzzer**

기존의 정상 입력인 시드(seed)를 조금씩 변형한다.

대표적인 변형 방법은 다음과 같다.

- 비트 뒤집기
- 바이트 삭제 또는 삽입
- 숫자를 0, -1, 최댓값 등으로 변경
- 문자열 길이 늘리기
- 입력의 일부 복제
- 여러 입력 조각 결합

특징:

- 입력 형식을 자세히 몰라도 시작할 수 있다.
- 구현이 비교적 간단하다.
- 좋은 시드가 있으면 효과가 높다.
- 구조가 복잡한 입력은 무작위 변형 과정에서 쉽게 깨질 수 있다.

---

**공통점과 차이점**

| 구분 | 생성 기반 | 변이 기반 |
| --- | --- | --- |
| 입력 생성 | 규칙에 따라 새로 생성 | 기존 입력을 변형 |
| 사전 지식 | 비교적 많이 필요 | 적게 필요 |
| 시드 필요성 | 필수가 아닌 경우가 많음 | 일반적으로 필요 |
| 입력 구조 유지 | 비교적 잘 유지 | 쉽게 깨질 수 있음 |
| 적합한 대상 | 프로토콜, 언어, 복잡한 파일 형식 | 일반 프로그램, 라이브러리, 파일 파서 |

두 방식 모두 다양한 입력을 반복적으로 전달해 프로그램의 오류를 찾는다는 점은 같다. 

실제 fuzzer에서는 두 방식을 혼합하기도 한다.

#### 3-2. 프로그램 내부 정보 활용 정도에 따른 분류

**⓵ 블랙박스 fuzzer**

대상 프로그램의 내부 구조를 확인하지 않고 입력과 출력만 관찰한다.

특징:

- 소스 코드가 없어도 사용할 수 있다.
- 실제 외부 공격자와 유사한 관점에서 테스트할 수 있다.
- 어떤 코드가 실행됐는지 알기 어렵다.
- 동일하거나 의미 없는 입력을 반복할 가능성이 있다.

---

⓶ **화이트박스 fuzzer**

소스 코드, 프로그램 경로, 조건문 등의 내부 정보를 적극적으로 분석한다. 

기호 실행이나 제약 조건 해결을 이용하기도 한다.

예를 들어 다음 조건을 통과해야 하는 경우를 생각할 수 있다.

```
if (a == 100 && b == 200) {
    crash();
}
```

화이트박스 fuzzer는 조건을 분석해 a=100, b=200과 같은 입력을 계산할 수 있다.

특징:

- 깊은 실행 경로에 도달할 가능성이 높다.
- 복잡한 조건문을 체계적으로 분석할 수 있다.
- 분석 비용과 실행 시간이 많이 든다.
- 대규모 프로그램에서는 경로 폭발 문제가 발생할 수 있다.

---

⓷ **그레이박스 fuzzer**

프로그램 내부를 완전히 분석하지는 않지만, 코드 커버리지와 실행 경로 같은 일부 정보를 활용한다.

동작 예:

1. 입력을 변형한다.
2. 대상 프로그램을 실행한다.
3. 새로운 코드 경로에 도달했는지 확인한다.
4. 새로운 경로를 발견한 입력을 보관한다.
5. 해당 입력을 다시 변형한다.

특징:

- 블랙박스보다 효율적이다.
- 화이트박스보다 빠르고 적용하기 쉽다.
- 현대적인 fuzzing에서 가장 널리 사용되는 방식 중 하나다.
- 계측이나 커버리지 수집 환경이 필요할 수 있다.

---

**세 방식 비교**

| 구분 | 블랙박스 | 그레이박스 | 화이트박스 |
| --- | --- | --- | --- |
| 내부 정보 활용 | 거의 없음 | 일부 활용 | 적극적으로 활용 |
| 소스 코드 필요성 | 보통 불필요 | 선택적 | 필요한 경우가 많음 |
| 실행 속도 | 빠름 | 빠른 편 | 느린 편 |
| 새로운 경로 탐색 | 낮음 | 높음 | 매우 정교함 |
| 분석 비용 | 낮음 | 중간 | 높음 |
| 대표 기술 | 무작위 입력 | 커버리지 기반 탐색 | 기호 실행, 제약 조건 해결 |

세 방식 모두 자동으로 많은 입력을 실행하고 오류를 찾는다는 목적은 같다.

가장 큰 차이는 대상 프로그램의 내부 정보를 얼마나 사용하는가이다.

#### 3- 3. 실행 방식에 따른 분류

⓵ **인프로세스 fuzzer**

fuzzer와 테스트 대상 코드가 같은 프로세스 안에서 실행된다.

예를 들어 libFuzzer에서는 테스트할 함수를 다음과 같이 작성한다.

```
int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size) {
    parse_data(data, size);
    return 0;
}
```

특징:

- 프로세스를 매번 실행하지 않아 매우 빠르다.
- 함수나 라이브러리 테스트에 적합하다.
- fuzzing용 테스트 하네스가 필요하다.
- 전체 애플리케이션의 실제 실행 환경과 차이가 있을 수 있다.

---

**⓶ 아웃오브프로세스 Fuzzing**

대상 프로그램을 별도 프로세스로 실행하고 외부에서 입력을 전달한다.

특징:

- 명령행 프로그램이나 서버 전체를 테스트하기 좋다.
- 대상 프로그램이 충돌해도 fuzzer가 함께 종료되지 않는다.
- 프로세스를 반복 실행하면 속도가 느려질 수 있다.
- 실제 프로그램 실행 환경을 비교적 잘 반영한다.

---

#### 3-4. 탐색 기술에 따른 분류

**⓵ 무작위 fuzzer**

입력을 무작위로 생성하거나 변형한다.

- 구조가 단순하다.
- 실행 속도가 빠르다.
- 복잡한 조건을 통과하기 어렵다.
- 간단한 예외 처리 오류를 발견하는 데 유용하다.

⓶ **커버리지 기반 fuzzer**

새로운 코드가 실행됐는지를 기준으로 유용한 입력을 선택한다.

- 새로운 경로를 발견한 입력을 우선적으로 보관한다.
- 같은 입력을 반복하는 낭비를 줄일 수 있다.
- AFL++, libFuzzer가 대표적이다.

**⓷ 문법 기반 fuzzer**

정해진 문법에 맞게 입력을 생성한다.

예를 들어 SQL 문법을 알고 있다면 다음과 같은 입력을 만들 수 있다.

```
SELECT name FROM users WHERE id = 1;
```

이후 연산자, 괄호, 자료형, 중첩 구조 등을 변화시킨다.

- 컴파일러, 브라우저, 데이터 형식 파서에 적합하다.
- 유효한 구조를 유지하면서 깊은 로직을 테스트할 수 있다.
- 문법 정의가 부정확하면 탐색 범위가 제한된다.

⓸ **상태 기반 fuzzer**

이전 요청과 응답에 따라 상태가 달라지는 대상을 테스트한다.

예를 들어 로그인 후에만 파일 업로드가 가능한 서비스라면 다음 순서를 유지해야 한다.

```
연결 → 로그인 → 인증 성공 → 파일 업로드 → 로그아웃
```

- 네트워크 프로토콜과 웹 API에 적합하다.
- 요청 순서와 세션 상태를 처리해야 하므로 복잡하다.
- 단일 입력만 변형하는 fuzzer보다 상태 오류를 발견하기 좋다.

⓹ **하이브리드 fuzzer**

그레이박스 fuzzing과 기호 실행 등 여러 기술을 결합한다.

- 일반적인 경로는 빠른 커버리지 기반 fuzzing으로 탐색한다.
- 어려운 조건문에서는 기호 실행을 사용한다.
- 탐색 능력이 높지만 시스템 구성이 복잡하고 자원이 많이 필요하다.

---

### 4. 대표적인 fuzzer

#### **4-1. AFL++**

AFL++는 기존 입력을 변형하고, 실행 피드백을 이용해 유용한 입력을 선택하는 퍼징 프레임워크다. 

AFL을 기반으로 다양한 계측 방식과 입력 변형 기법 등을 확장했다.

예를 들어 PNG 파서를 테스트한다면, 시드 파일의 일부를 변경해 실행한 뒤 새로운 실행 특징이 관찰되는지 확인한다. 

탐색에 도움이 되는 입력은 코퍼스에 보관하고 다시 변형한다. 여기서 코퍼스(corpus)는 퍼징에 사용하는 입력들의 집합을 뜻한다.

소스 코드가 있으면 컴파일 과정에서 계측을 추가할 수 있다. 

소스 코드가 없는 경우에도 지원되는 환경에서 QEMU 등의 바이너리 계측 방식을 사용할 수 있다. 

따라서 소스 코드가 없다는 이유만으로 블랙박스 퍼징으로 한정되는 것은 아니다.

입력 변형과 실행을 담당하는 afl-fuzz 외에 코퍼스 최소화와 오류 입력 최소화 도구도 제공한다. 

C/C++ 실행 파일이나 파일 파서를 대상으로, 입력 탐색부터 발견한 입력 정리까지 구성하기 좋다. 

다만 입력이 초기에 모두 거부된다면 시드, 사전, 하네스 등을 개선해야 한다.

#### **4-2. libFuzzer**

libFuzzer는 테스트 대상 코드와 같은 프로세스에서 동작하는 커버리지 기반 퍼징 엔진이다. 

개발자가 입력 바이트를 받는 함수를 작성하면 libFuzzer가 다양한 입력으로 그 함수를 반복 호출한다.

대표적인 테스트 함수 형태는 다음과 같다.

```
int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size) {
    parse_data(data, size);
    return 0;
}
```

이 함수처럼 퍼저가 만든 입력을 실제 테스트 대상에 연결하는 코드를 하네스(harness)라고 한다. 

하네스에서 어떤 API를 어떤 순서로 호출하느냐에 따라 테스트 범위가 달라진다.

반복마다 프로세스를 새로 시작하는 비용을 줄일 수 있어 함수나 라이브러리 테스트에 적합하다.

AddressSanitizer 등의 검사 도구와 함께 사용하면 정상 실행에서는 드러나지 않는 메모리 오류도 발견할 수 있다.

반면 전역 변수나 객체 상태가 반복 사이에 남으면 이전 입력이 다음 실행에 영향을 줄 수 있다. 

하네스는 반복 실행을 고려해 상태를 관리해야 한다. 

공식 문서에는 주요 신규 기능 개발보다 중요한 버그 수정 지원을 계속하는 상태라고 안내되어 있다.

#### **4-3. Honggfuzz**

Honggfuzz는 실행 피드백을 바탕으로 입력을 발전시키는 범용 퍼저다. 

소프트웨어 계측으로 수집한 커버리지와, 지원되는 환경에서 하드웨어 기반 실행 정보를 활용할 수 있다.

일반적인 실행 프로그램을 별도 프로세스로 시험할 수 있고, 대상 API를 반복 호출하는 지속 실행 방식도 지원한다. 

따라서 함수·라이브러리 전용 엔진으로 한정해서 설명하기보다는 여러 실행 방식과 피드백 수집 방식을 지원하는 퍼저로 이해하는 것이 적절하다.

예를 들어 파일을 받아 처리하는 프로그램에 변형한 파일을 전달하고, 실행 결과와 커버리지를 관찰하며 다음 입력을 선택한다. 

지속 실행 방식으로 구성하면 프로세스 시작 비용을 줄일 수 있다.

AFL++와 모두 피드백 기반 탐색을 수행하지만, 사용할 수 있는 계측 방식과 운영 환경, 실행 설정 등이 다르다. 

하드웨어 기반 기능도 모든 운영체제와 CPU에서 동일하게 사용할 수 있는 것은 아니다.

#### **4-4. Jazzer**

Jazzer는 Java·Kotlin 등 JVM에서 실행되는 코드를 위한 인프로세스 퍼저다. 

libFuzzer를 기반으로 하며, 코드 실행 피드백을 이용해 입력을 생성하고 변형한다.

JUnit과 통합할 수 있어 기존 단위 테스트와 함께 퍼징 테스트를 작성할 수 있다. 

문자열, 배열 등 여러 형태의 인자를 생성해 파서, 직렬화 코드, 입력 검증 함수 등을 반복적으로 시험할 수 있다.

예를 들어 문자열을 인코딩하고 다시 디코딩하는 기능을 테스트한다면, 다양한 문자열에 대해 다음 조건을 확인할 수 있다.

```
decode(encode(input)) == input
```

이러한 검증 조건을 작성하면 예외나 충돌이 발생하지 않아도 잘못된 결과를 발견할 수 있다. 

다만 위 관계가 해당 API의 명세상 성립하는지 먼저 확인해야 한다.

Jazzer가 입력 탐색을 자동화하더라도, 어떤 결과를 오류로 판단할 것인지는 테스트 코드에 적절히 표현해야 한다.

#### **4-5. Atheris**

Atheris는 Python 코드와 네이티브 확장 모듈을 테스트할 수 있는 커버리지 기반 퍼저다. 

Python 바이트코드에 계측을 추가해 실행 정보를 수집하고 입력 탐색에 활용한다.

개발자는 입력을 받는 테스트 함수를 작성하고, 그 안에서 시험할 라이브러리를 호출한다. 

예를 들어 바이트 데이터를 해석하는 파서나 직렬화 라이브러리에 여러 입력을 전달하도록 구성할 수 있다.

Python 코드에서 처리되지 않은 예외가 발생하면 실패로 보고한다. 

이때 잘못된 형식의 입력에 대해 의도적으로 발생시키는 예외와, 예상하지 못한 예외를 구분해야 한다.

정상적인 입력 거부 예외는 하네스에서 처리할 수 있지만, 모든 예외를 무조건 무시하면 실제 버그도 놓칠 수 있다.

또한 테스트할 코드에 계측이 적용되어야 실행 정보를 제대로 활용할 수 있다.

#### **4-6. go-fuzz**

go-fuzz는 Go 패키지를 대상으로 하는 커버리지 기반 퍼징 도구다. 

복잡한 텍스트나 바이너리 입력을 처리하는 패키지를 테스트하는 데 활용할 수 있다.

일반적으로 다음 형태의 테스트 함수를 작성한다.

```
func Fuzz(data []byte) int
```

퍼저가 생성한 바이트 데이터를 이 함수에 전달하고, 함수 안에서 테스트 대상 코드를 호출한다. 

실행 중 panic, 충돌, 멈춤 등의 문제를 찾을 수 있으며, 별도의 검증 조건을 작성해 논리적 오류도 확인할 수 있다.

특징적인 부분은 반환값으로 입력의 취급에 영향을 줄 수 있다는 점이다. 

예를 들어 파싱에 성공한 입력의 우선순위를 높이거나, 특정 입력이 코퍼스에 추가되지 않도록 지정할 수 있다. 

이는 커버리지 외에 테스트 작성자의 지식을 입력 탐색에 반영하는 수단이다.

go-fuzz는 Go 표준 도구에 포함된 내장 퍼징과 별개의 도구다. 문서에서는 두 이름을 구분해서 사용해야 한다.

#### **4-7. Peach**

Peach는 입력의 구조와 통신 상태를 모델로 정의해 사용하는 퍼징 플랫폼이다. 생성 기반과 변이 기반 퍼징을 모두 지원한다.

Peach Pit이라는 설정 파일에 데이터의 자료형과 구조, 필드 사이의 관계 등을 작성한다. 

예를 들어 패킷에 길이 필드와 데이터 필드가 있다면 두 필드의 관계를 표현할 수 있다. 

이를 통해 구조를 고려한 입력을 만들거나 변형할 수 있다.

상태 모델로 메시지를 주고받는 절차를 구성하고, Publisher로 입력 전달 방식을, Monitor 등으로 오류 관찰 방식을 설정한다. 

따라서 단순한 입력 생성기보다 여러 구성 요소를 연결하는 플랫폼에 가깝다.

복잡한 파일 형식이나 프로토콜을 체계적으로 표현할 수 있지만, 모델을 작성하는 데 대상에 대한 지식이 필요하다. 

정의한 모델의 범위와 정확성이 테스트 범위에도 영향을 준다.

#### 4-8. Radamsa

Radamsa는 기존 데이터를 변형해 새로운 테스트 입력을 만드는 데 집중하는 도구다. 

정상적인 파일이나 메시지를 받아 여러 변형을 적용한다.

예를 들어 정상 JSON 문서나 이미지 파일을 입력으로 주고, 구조의 일부가 바뀌거나 데이터가 삽입·삭제된 결과를 생성하도록 사용할 수 있다. 

입력 형식을 상세하게 정의하지 않아도 시작하기 쉽다.

기본적으로 AFL++처럼 대상의 코드 커버리지를 직접 수집해 입력 선택에 활용하는 도구는 아니다. 

일반적인 구성에서는 별도 스크립트가 변형 결과를 프로그램에 전달하고, 종료 상태나 시간 초과를 확인한다.

따라서 입력 변형기를 기존 테스트 환경에 연결하고 싶을 때 유용하다. 

실행과 오류 감시까지 포함한 전체 환경은 사용자가 함께 구성해야 한다.

#### 4-9. KLEE

KLEE는 LLVM을 기반으로 하는 동적 기호 실행 엔진이다. 

구체적인 입력을 무작위로 계속 바꾸는 대신, 입력을 기호로 취급하고 프로그램의 분기 조건을 분석해 테스트 입력을 생성한다.

예를 들어 프로그램이 a == 100 && b == 200일 때 특정 경로로 이동한다면, 해당 조건을 제약식으로 표현하고 이를 만족하는 입력을 구할 수 있다. 

생성한 구체적인 입력으로 실제 프로그램의 동작을 확인할 수 있다.

이런 특성 때문에 화이트박스 테스트와 입력 생성의 사례로 활용된다. 

다만 KLEE 자체의 정확한 성격은 기호 실행 엔진이며, AFL++와 같은 변이 기반 퍼저와 작동 원리가 다르다.

분기가 늘어나면 분석할 상태가 급격히 증가하는 경로 폭발 문제가 발생할 수 있다. 

외부 라이브러리와 시스템 동작을 어떻게 모델링하는지, 제약식이 얼마나 복잡한지도 분석 가능 범위에 영향을 준다.

#### 4-10. boofuzz

boofuzz는 프로토콜 메시지와 통신 절차를 정의해 테스트하는 퍼징 프레임워크다. 

메시지의 문자열·정수·길이 등의 필드를 정의하고, 값을 변형해 대상에 전달한다.

요청 사이의 연결 관계를 구성할 수 있어 “연결 → 인증 → 명령 실행”과 같은 절차를 시험할 수 있다. 

단일 메시지뿐 아니라 이전 요청이 필요한 상황도 표현할 수 있다.

데이터 생성 외에도 테스트 기록, 실패 감지, 실패 후 대상 재설정 등의 기능을 제공한다. 

네트워크를 비롯한 여러 통신 방식과 연결할 수 있다.

기본적인 사용에서는 사용자가 메시지 구조와 요청 절차를 정의한다. 

따라서 프로토콜에 대한 이해와 모델 작성이 중요하며, AFLNet처럼 응답으로 추정한 상태를 자동 탐색에 활용하는 방식과 구분해서 설명할 수 있다.

#### 4-11. SQLancer

SQLancer는 데이터베이스 시스템의 논리적 오류 등을 찾는 자동화 테스트 도구다. 

테이블·데이터·SQL 질의를 생성하고, 테스트 오라클을 이용해 실행 결과를 검증한다.

오라클은 실행 결과가 올바른지 판단하는 기준이다. 

데이터베이스가 충돌하지 않고 결과를 반환했더라도, 반환한 행이 누락되었다면 논리적 오류가 될 수 있다.

SQLancer의 NoREC는 최적화가 적용될 수 있는 질의를 최적화가 거의 적용되지 않는 형태로 변환해 결과를 비교한다. 

TLP는 질의를 논리적으로 분할한 뒤 결과를 조합해 원래 결과와 비교한다.

따라서 SQLancer는 충돌 탐지 중심의 퍼징에서 결과 검증 중심의 테스트로 범위를 넓히는 사례다. 

적용 가능한 SQL 기능과 탐지할 수 있는 오류는 DBMS 지원 범위와 선택한 오라클에 따라 달라진다.

### 5. 대표적인 fuzzer 비교

| fuzzer | 주요 대상 | 주요 방식 | 특징 |
| --- | --- | --- | --- |
| AFL++ | C/C++ 프로그램, 실행 파일 | 변이·그레이박스 | 커버리지 기반이며 다양한 실행 모드 지원 |
| libFuzzer | C/C++ 함수·라이브러리 | 인프로세스·그레이박스 | 빠르며 Sanitizer와 연동하기 좋음 |
| Honggfuzz | 네이티브 프로그램 | 변이·그레이박스 | 하드웨어 카운터 및 다양한 실행 방식 지원 |
| Jazzer | Java/JVM | 커버리지 기반 | Java 라이브러리와 JVM 코드에 적합 |
| Atheris | Python | 커버리지 기반 | Python 코드와 확장 모듈 테스트 가능 |
| go-fuzz | Go | 커버리지 기반 | Go 함수와 패키지 fuzzing에 사용 |
| Peach | 파일·프로토콜 | 생성·문법·상태 기반 | 복잡한 데이터 모델과 프로토콜에 적합 |
| Radamsa | 범용 입력 | 변이 기반 | 사용하기 간단하지만 커버리지 피드백은 제한적 |
| KLEE | LLVM 기반 프로그램 | 화이트박스 | 기호 실행으로 조건을 만족하는 입력 생성 |
| boofuzz | 네트워크 프로토콜 | 생성·상태 기반 | 네트워크 요청과 세션 순서 테스트에 적합 |
| SQLancer | 관계형 데이터베이스 시스템 | SQL·데이터 생성·오라클 기반 검증 | 질의 결과의 관계를 검증해 잘못된 결과를 반환하는 논리적 오류 등 탐지 |

참고로 하나의 fuzzer가 반드시 하나의 분류에만 속하는 것은 아니다. 

예를 들어 AFL++는 변이 기반이면서 그레이박스 방식이고, 주로 커버리지 정보를 이용하는 fuzzer다.

### 6. fuzzer들의 공통점

- **테스트 입력을 자동으로 마련한다.**

사람이 모든 테스트 데이터를 직접 작성하는 부담을 줄인다. 

기존 입력을 변형하거나, 입력 구조에 따라 생성하거나, 프로그램의 조건을 분석해 새로운 입력을 만든다.

입력은 바이트 데이터, 파일, 함수의 인자, 프로토콜 메시지, SQL 질의 등 대상에 따라 달라진다.

- **다양한 입력으로 프로그램의 오류를 찾는 데 활용한다.**

일반적인 입력뿐 아니라 빈 데이터, 극단적인 숫자, 복잡한 구조, 예상하지 못한 메시지 등을 시험한다. 

이를 통해 사람이 작성한 테스트에서 놓치기 쉬운 상황을 탐색한다.

다만 입력 생성부터 실행·감시까지 자동화하는 도구도 있고, Radamsa처럼 생성한 입력을 별도 실행 환경에 연결해야 하는 도구도 있다.

- **테스트 대상과 연결하는 준비가 필요하다.**

함수를 호출하는 하네스, 정상 입력인 시드, 프로토콜의 데이터 모델, 오류 검증 조건 등을 준비해야 한다. 

무엇을 어떻게 연결하느냐에 따라 실제 테스트 범위가 달라진다.

- **오류를 판단할 기준이 필요하다.**

충돌, 시간 초과, 처리되지 않은 예외, 메모리 검사 도구의 오류 보고, 검증 조건 위반 등을 확인한다. 

SQLancer처럼 질의 결과의 관계를 비교해 논리적 오류를 찾는 경우도 있다.

- **발견한 문제는 재현하고 분석해야 한다.**

실패한 입력이 발견되었다고 보안 취약점이 바로 확정되지는 않는다. 

입력을 다시 실행하고, 불필요한 부분을 줄이며, 원인과 영향을 확인해야 한다.

### 7. 핵심 차이점

#### 7-1. 테스트 대상과 도구의 역할

| 도구 | 주요 대상 | 중심 역할 |
| --- | --- | --- |
| AFL++ | 네이티브 실행 파일·라이브러리·파일 파서 | 입력 변형과 실행 피드백을 이용한 탐색 |
| libFuzzer | 주로 C/C++ 함수·라이브러리 | 같은 프로세스에서 테스트 함수를 반복 호출 |
| Honggfuzz | 네이티브 프로그램·라이브러리 | 소프트웨어·하드웨어 실행 피드백을 활용한 탐색 |
| Jazzer | Java·Kotlin 등 JVM 코드 | JVM 코드에 대한 커버리지 기반 퍼징 |
| Atheris | Python 코드·네이티브 확장 모듈 | Python 및 확장 코드에 대한 퍼징 |
| go-fuzz | Go 패키지 | Go 테스트 함수를 통한 커버리지 기반 탐색 |
| Peach | 구조화된 파일·프로토콜 | 데이터·상태 모델에 따른 입력 생성과 변형 |
| Radamsa | 다양한 형식의 기존 입력 | 입력 변형 |
| KLEE | LLVM 기반으로 분석할 수 있는 프로그램 | 기호 실행으로 조건을 만족하는 입력 생성 |
| boofuzz | 네트워크 프로토콜·통신 프로그램 | 메시지 구조와 요청 절차를 정의한 테스트 |
| SQLancer | 관계형 데이터베이스 시스템 | SQL·데이터 생성과 결과 검증 |

#### 7-2. 입력 생성 방식

변이 기반 도구는 기존 입력을 바꾸어 새로운 입력을 만든다. 

AFL++, libFuzzer, Honggfuzz, Radamsa, go-fuzz 등이 대표적인 사례다. 

Jazzer와 Atheris도 입력 변형을 활용한다.

모델 기반 도구는 입력 구조나 자료형, 필드 관계 등을 활용한다. 

Peach는 생성과 변이를 모두 지원하며, boofuzz는 메시지의 필드와 통신 절차를 정의해 시험한다.

조건 분석 방식을 사용하는 KLEE는 분기 조건을 제약식으로 분석한다. 

예를 들어 특정 값이 입력되어야 통과하는 조건을 분석해 그 값을 구할 수 있다.

SQLancer는 데이터베이스 상태와 SQL 질의를 생성하고, 선택한 오라클로 결과를 검증한다. 

따라서 입력 생성과 함께 정답 여부를 어떻게 판단하는가가 중요한 특징이다.

#### 7-3. 실행 피드백의 활용

| 구분 | 해당 도구 | 특징 |
| --- | --- | --- |
| 커버리지 등의 피드백으로 탐색 | AFL++, libFuzzer, Honggfuzz, Jazzer, Atheris, go-fuzz | 새로운 실행 특성을 보인 입력을 다음 탐색에 활용 |
| 정의한 모델·절차를 중심으로 시험 | Peach, boofuzz | 데이터 구조와 상태·요청 관계에 따라 테스트 구성 |
| 대상의 커버리지 피드백 없이 입력 변형 | Radamsa | 실행·감시 환경을 별도로 연결하는 경우가 일반적 |
| 프로그램 조건을 분석 | KLEE | 기호 실행과 제약 조건 해결로 입력 생성 |
| 질의 결과 검증을 중심으로 시험 | SQLancer | 오라클로 논리적 오류 등을 탐지하며, 실행 계획 피드백을 활용하는 방식도 지원 |

커버리지는 다음에 탐색할 입력을 고르는 정보이고, 오라클은 실행 결과가 잘못되었는지 판단하는 기준이다. 두 역할을 구분해야 한다.

#### **7-4. 실행 방식과 상태 관리**

libFuzzer는 같은 프로세스에서 대상 함수를 반복 호출한다. 

Jazzer도 인프로세스 방식이며, Atheris와 go-fuzz도 작성한 테스트 함수를 반복 실행한다. 

이런 구성에서는 이전 실행의 전역 변수·캐시 등이 다음 실행에 영향을 주지 않도록 관리해야 한다.

AFL++와 Honggfuzz는 여러 실행 모드를 제공한다. 

별도 대상 프로세스를 관리하면서도 persistent mode 등으로 반복 실행 비용을 줄일 수 있다.

Peach와 boofuzz는 메시지를 주고받는 절차와 대상 상태가 중요하다. 

SQLancer에서는 테이블과 데이터 등 데이터베이스 상태 자체가 테스트의 일부가 된다.

#### **7-5. 오류를 찾는 방법**

충돌을 관찰하는 것만으로 모든 오류를 발견할 수는 없다.

- 메모리 오류: AFL++·libFuzzer·Honggfuzz 등을 메모리 검사 도구와 함께 사용한다.
- 예외·검증 조건 위반: Jazzer·Atheris·go-fuzz 등의 테스트 함수에서 확인한다.
- 통신 중 실패: Peach·boofuzz에 연결한 감시 기능으로 확인한다.
- 분석 중 오류와 경로 조건: KLEE의 기호 실행으로 확인한다.
- 잘못된 질의 결과: SQLancer의 테스트 오라클로 확인한다.
- Radamsa가 만든 입력의 오류 여부: 별도의 실행·감시 환경에서 확인한다.

이 구분은 대표적인 사용 방식이며, 하네스에 검증 조건을 추가하면 여러 도구로 논리적 오류를 시험할 수도 있다.

### 8. 간단한 선택 기준

| 테스트 상황·목적 | 우선 검토할 도구 | 선택 이유 |
| --- | --- | --- |
| 네이티브 실행 파일이나 파일 파서를 시험하고 싶다 | AFL++ | 커버리지 기반 탐색과 여러 계측·실행 방식 제공 |
| 특정 C/C++ 함수를 직접 반복 호출할 수 있다 | libFuzzer | 함수 단위 하네스와 인프로세스 실행에 적합 |
| 네이티브 대상을 다양한 실행 피드백으로 시험하고 싶다 | Honggfuzz | 소프트웨어·하드웨어 피드백과 여러 실행 방식 지원 |
| Java·Kotlin 코드를 시험한다 | Jazzer | JVM 계측과 JUnit 통합 지원 |
| Python 코드나 확장 모듈을 시험한다 | Atheris | Python 커버리지와 네이티브 코드 테스트 지원 |
| go-fuzz 방식의 하네스로 Go 패키지를 시험한다 | go-fuzz | Go 패키지용 커버리지 기반 탐색 제공 |
| 복잡한 입력 구조와 필드 관계를 모델링해야 한다 | Peach | 데이터·상태 모델을 활용한 생성과 변형 지원 |
| 기존 테스트 환경에 입력 변형 기능을 붙이고 싶다 | Radamsa | 입력 변형기로 연결해 활용하기 좋음 |
| 분기 조건을 분석해 통과할 입력을 구하고 싶다 | KLEE | 기호 실행과 제약 조건 해결 활용 |
| 프로토콜 메시지와 요청 순서를 직접 정의하고 싶다 | boofuzz | 메시지 필드와 통신 절차를 구성하기 좋음 |
| DBMS가 잘못된 SQL 결과를 반환하는지 확인하고 싶다 | SQLancer | 질의 결과를 검증하는 오라클 제공 |

선택할 때는 대상 언어·실행 환경 → 입력을 연결할 방법 → 활용 가능한 피드백 → 찾으려는 오류 순서로 확인하면 된다. 

예를 들어 C/C++ 라이브러리라도 함수 하네스를 작성할 수 있는지, 실행 파일 형태로만 시험할 수 있는지에 따라 libFuzzer와 AFL++ 중 검토할 도구가 달라진다.

또한 go-fuzz는 Go 내장 퍼징과 별도 프로젝트다. 

새 Go 테스트 환경을 구성할 때는 표준 go test에 통합된 내장 퍼징도 함께 비교할 수 있다.
