- **초록**

도구 선택은 LLM 에이전트의 핵심

검색과 선택 이라는 두 단계를 통해 도구 라이브러리에서 도구 선택

no-box 시나리오에 나오는 ToolHijacker라는 프롬프트 인젝션에 대해 소개함

ToolHijacker는 도구 라이브러리에 악성 도구를 주입하고 그 도구를 선택하도록 함

특정 작업에 악성 도구를 선택되도록 강제함

ToolHijacker는 기존 프롬프트 인젝션 보다 효과가 좋음

여러 방어 방법을 적용하여 방어를 해봄

하지만 실험 결과는 기존에 있던 방식으로는 불충분함을 보여줌

새로운 방어 전략 개발이 시급함을 강조함

**I.서론**

LLM 성능이 뛰어나서 여러 종류 에이전트가 개발됨

에이전트 작동의 핵심 3단계: 계획, 도구 선택, 도구 호출

도구 선택은 검색과 선택이라는 접근법을 사용함

에이전트는 신뢰할 수 없는 외부 출처를 통합하므로 프롬프트 인젝션에 취약함

공격자는 외부 출처에 유해한 지시를 주입하여 에이전트의 행동을 공격자의 의도에 맞게 조작

프롬프트 인젝션은 자동과 수동으로 나뉨

수동은 개발 시간 투자 많고 서로 다른 시나리오에서 일반화가 제한적임

자동은 최적화 프레임워크를 사용함(JudgeDeceiver, PoisonedRAG)

LLM을 겨냥한 주입 프롬프트를 생성하며, 특히 도구 선택 조작에 초점을 맞춤

하지만 기존 방식으로는 도구 선택에서 여전히 최적에 미치지 못함

수동과 JudgeDeceiver의 한계는 모두 선택 단계에 집중하지만, 종단 간 공격으로서 불완전하여 발생함

PoisonedRAG는 검색 단계를 고려하지만, 도구 선택을 직접 조작하기보다는 여러 악성 항목을 지식 기반에 주입하여 생성에 집중함

차이는 도구 선택 프롬프트 주입에 고유한 과제를 만들며, 본 연구는 이를 다룸

no-box 시나리오에서 도구 선택을 표적으로 삼는 최초의 프롬프트 인젝션인 ToolHijacker를 제안함

ToolHijacker는 프롬프트 인젝션을 통해 도구 선택을 조작하는 악성 도구 문서를 효율적으로 생성함

생성된 문서가 도구 라이브러리에 주입되면 검색과 선택 단계 모두에 영향을 주어 LLM 에이전트가 악성 도구를 선택하도록 강제함

사용자가 같은 작업을 다양하게 표현해도 ToolHijacker는 도구 선택을 일관된 제어를 보장함

ToolHijacker는 도구 라이브러리와 시스템 내부 정보를 알 수 없는 no-box 환경에서도 작동하도록 설계됨

- (그림1)
    
    사용자가 LLM 에이전트에게 질문을 했을 때 위쪽은 공격이 없는 경우를, 아래쪽은 공격이 있는 경우를 설명함.
    
    공격이 없는 경우 도구 라이브러리에서 정상 도구를 검색 및 선택을 함
    
    공격이 있는 경우 도구 라이브러리에서 검색할 때 악성 도구를 강제 선택하게 함
    

ToolHijacker는 실제 시스템의 정보를 알 수 없는 no-box 환경을 대신하기 위해 유사한 대리 환경을 먼저 구성함

이후 악성 도구가 검색 후보에 포함되고 최종적으로 선택되도록 도구 설명을 최적화함

문장 전체를 한 번에 최적화하기 어려우므로 도구 설명을 검색을 위한 부분과 선택을 유도하는 부분으로 나누어 각각 최적화한 뒤 하나로 합침

두 데이터셋에서 8개 LLM과 4개 검색기를 대상으로 실험한 결과, ToolHijacker는 no-box 환경에서 높은 공격 성공률을 보임

대리 LLM과 표적 LLM의 구조가 달라도 높은 성능을 유지했으며, 검색 단계에서도 높은 성공률을 기록함

또한 기존의 여러 프롬프트 주입 공격보다 뛰어난 성능을 보임

두 가지 예방 기반 방어와 네 가지 탐지 기반 방어를 평가한 결과, 기존 방어 방법들은 ToolHijacker를 효과적으로 막지 못함

예방 기반 방어가 적용된 상태에서도 공격 성공률이 높았으며, 탐지 기반 방어 역시 일부 악성 문서만 탐지하고 대부분을 놓쳣음

**II.문제 정식화**

이 절은 도구 선택 프레임워크를 형식적으로 정의하고, 공격자의 목표, 배경지식, 능력을 바탕으로 위협 모델을 규정함

A) 도구 선택 

사용자의 질문과 유사한 상위 k개의 도구를 먼저 검색한 뒤, LLM이 구조화된 프롬프트를 바탕으로 후보 중 가장 적절한 도구 하나를 최종 선택함

| 수식 | 설명 |
| --- | --- |
| 식 (1) | 전체 도구 중 사용자 질문과 관련성이 높은 상위 k개의 도구를 후보로 가져옴 |
| 식 (2) | 사용자 질문과 각 도구 설명을 숫자 벡터로 바꾸고, 의미가 얼마나 비슷한지 계산해 검색 순위를 정함 |
| 식 (3) | LLM이 사용자 질문과 검색된 후보들을 보고 최종적으로 사용할 도구 하나를 선택함 |
| 식 (4) | 머리말 지시, 사용자 질문, 후보 도구들의 이름·설명, 꼬리말 지시를 하나의 프롬프트로 연결해 LLM에 입력하고 선택된 도구 이름을 출력함 |

- (그림2)
    
    선택 단계에서 LLM이 사용자 질문과 검색된 상위 \(k\)개의 도구 이름·설명을 함께 확인한 뒤, 가장 적합한 도구 하나를 선택하고 그 이름만 JSON 형식으로 출력하는 과정을 보여 줌
    

B) 위협 모델

공격 목표: 공격자는 특정 작업만 알고 있으며, 사용자가 그 작업을 어떤 방식으로 질문하더라도 정상 도구 대신 악성 도구가 우선 선택되게 하려고 함

이를 위해 도구 선택에 큰 영향을 주는 도구 이름과 설명을 조작함

공격자의 정보: 실제 사용자 질문, 도구 라이브러리, 검색 결과 수 k, 검색기와 LLM의 내부 정보에 접근할 수 없고 직접 시험할 수도 없는 no-box 환경임

공격자의 능력: 실제 환경 대신 별도의 질문·도구 문서·검색기·LLM으로 대리 환경을 만들어 악성 도구 문서를 개발하고, 개방형 도구 플랫폼에 게시할 수 있음

위험성: LLM 에이전트가 선택한 도구를 별도의 검증 없이 실행하면 결과 조작, 개인정보 침해 등의 보안 문제가 발생할 수 있음

**III. ToolHijacker**

A) 개요

ToolHijacker는 실제 시스템 정보를 알 수 없는 no-box 환경에서 대리 파이프라인을 이용해 악성 도구 문서를 자동으로 생성함

문서 전체를 한 번에 최적화하기 어렵기 때문에 검색을 위한 부분 R과 최종 선택을 유도하는 부분 S으로 나누어 각각 최적화한 뒤 하나로 결합함

이를 위해 기울기 비사용 방법과 기울기 기반 방법을 사용함

B) 최적화 문제 정식화

실제 시스템에 접근할 수 없는 no-box 환경을 대신하기 위해, 접근 가능한 LLM으로 다양한 대리 작업 설명을 만들고 관련·비관련 도구가 섞인 대리 도구 라이브러리를 구성함

이 환경에서 다양한 표현의 작업이 주어져도 악성 도구가 검색되고 최종 선택되는 비율을 최대화하도록 악성 도구 문서를 최적화함

텍스트는 이산적이고 미분하기 어려우므로, 도구 설명을 검색 후보에 포함시키기 위한 부분 R과 최종 선택을 유도하는 부분 S으로 나누어 순서대로 최적화함

도구 이름은 사람이 작성하고 도구 설명은 기울기 기반 또는 기울기 비사용 방법으로 최적화함

| 수식 | 설명 |
| --- | --- |
| 식 (5) | 여러 대리 질문으로 시험했을 때 악성 도구가 최종 선택되는 비율이 최대가 되도록 악성 도구 문서를 만듦 |

C) 검색을 위한 R 최적화

R 최적화의 목적은 악성 도구 문서가 다양한 작업 설명과 높은 관련성을 가져 검색 결과 상위 k’개에 포함되도록 하는 것임

기울기 비사용 방법은 LLM이 여러 대리 작업 설명의 공통 기능을 추출하여 일반적인 도구 설명 R을 생성함

기울기 기반 방법은 이 설명을 초기값으로 사용하고, 대리 검색기의 기울기 정보와 HotFlip을 이용해 작업 설명과의 평균 유사도가 높아지도록 토큰을 수정함

검색 모델들이 학습한 의미 패턴이 비슷하기 때문에, 대리 검색기에서 최적화한 R이 실제 표적 검색기에도 적용될 수 있음

| 수식 | 설명 |
| --- | --- |
| 식 (6) | 여러 대리 질문과 악성 도구 설명의 평균 유사도가 최대가 되도록 R을 수정함 |

D) 선택을 위한 S 최적화

R을 먼저 최적화한 뒤, 악성 도구 설명 R⊕S의 S를 최적화하여 검색된 후보 중 악성 도구가 최종 선택되도록 함

각 대리 질문마다 정상 대리 도구 k′-1개와 악성 도구를 합쳐 총 k′개의 후보를 구성하고, 다양한 질문에서 대리 LLM이 악성 도구를 일관되게 선택하도록 S를 최적화함

**기울기 비사용:** 공격자 LLM이 기존 S를 바탕으로 여러 변형을 생성하고, 대리 LLM이 각 변형을 모든 대리 질문에서 평가함

대리 LLM이 악성 도구를 선택한 횟수를 기준으로 성능이 좋은 상위 후보만 남기고, 평가 결과를 피드백으로 제공하면서 생성과 평가를 반복함

모든 대리 질문에서 악성 도구 선택에 성공한 후보가 나오면 최적화를 종료함. 그렇지 않으면 가장 높은 성공 횟수를 기록한 S를 최종 선택함

**기울기 기반:** 대리 LLM의 기울기 정보를 이용하여 악성 도구 이름이 출력될 가능성이 높아지도록 S의 토큰을 수정함

원하는 전체 선택 결과를 생성하도록 하는 정렬 손실, 악성 도구 이름의 생성을 강조하는 일관성 손실, 문장의 가독성을 높이는 퍼플렉서티 손실을 함께 사용함

세 손실의 중요도는 하이퍼파라미터 α와 β로 조절하고, 모든 대리 질문에서 전체 손실이 최소가 되도록 S를 최적화함

| 수식 | 설명 |
| --- | --- |
| 식 (7) | 여러 대리 질문에서 악성 도구가 최종 선택되는 비율이 최대가 되도록 S를 최적화함 |
| 식 (8) | 모든 대리 질문에서 대리 LLM이 악성 도구 이름을 출력할 확률이 최대가 되도록 S를 수정함 |
| 식 (9) | 대리 LLM이 원하는 전체 선택 결과를 출력할 확률이 높아지도록 정렬 손실을 계산함 |
| 식 (10) | 원하는 전체 출력을 구성하는 토큰들이 순서대로 생성될 확률을 계산함 |
| 식 (11) | 대리 LLM이 악성 도구 이름을 출력할 확률이 높아지도록 일관성 손실을 계산함 |
| 식 (12) | S가 지나치게 부자연스러운 문장이 되지 않도록 가독성과 자연스러움에 관한 손실을 계산함 |
| 식 (13) | 정렬 손실, 일관성 손실, 퍼플렉서티 손실을 가중치를 적용하여 하나의 전체 손실로 결합함 |
| 식 (14) | 모든 대리 질문에서 발생한 전체 손실의 합이 최소가 되도록 S를 최적화함 |

**IV. 평가**

A) 실험 설정

MetaTool과 ToolBench 데이터셋을 사용하여 ToolHijacker를 평가함

각 데이터셋에서 표적 작업 10개를 선정하고, 작업마다 다양한 표현의 작업 설명 100개를 생성하여 데이터셋별로 총 1,000개의 작업 설명을 사용함

ToolHijacker를 수동 프롬프트 주입 공격 5개와 자동 공격 2개인 JudgeDeceiver, PoisonedRAG와 비교함

오픈 소스와 비공개 소스를 포함한 8개 LLM과 4개 검색기를 표적으로 실험하여, 다양한 모델과 검색 환경에서 공격이 작동하는지 평가함

기울기 비사용 방법은 Llama-3.3-70B를 대리 LLM으로 사용하고, 기울기 기반 방법은 Contriever와 Llama-3-8B를 대리 검색기와 대리 LLM으로 사용함

평가 지표:

- ACC: 공격이 없을 때 정상 도구를 올바르게 선택하는 비율
- ASR: 공격이 있을 때 악성 도구가 최종 선택되는 비율
- HR: 정상 도구가 검색 결과 상위 k개에 포함되는 비율
- AHR: 악성 도구가 검색 결과 상위 k개에 포함되는 비율

| 수식 | 설명 |
| --- | --- |
| 식 (15) | 정상 도구가 검색 결과 상위 k개에 포함되는 비율인 HR을 계산함 |
| 식 (16) | 악성 도구가 검색 결과 상위 k개에 포함되는 비율인 AHR을 계산함 |

B) 주요 결과

ToolHijacker는 두 데이터셋과 8개 표적 LLM에서 높은 ASR과 AHR을 달성함

대리 LLM과 실제 표적 LLM의 구조가 달라도 높은 공격 성능을 유지하여, 한 모델에서 만든 악성 도구 문서가 다른 모델에도 적용될 수 있음을 보여 줌

GPT-4o를 표적으로 했을 때 기울기 비사용 방법의 ASR은 MetaTool에서 96.7%, ToolBench에서 88.2%였으며, 기울기 기반 방법은 각각 92.2%와 83.9%를 기록함

기울기 비사용 방법은 비공개 소스 모델에서 상대적으로 높은 성능을 보였고, 기울기 기반 방법은 오픈 소스 모델에서 더 높은 성능을 보임

모델마다 공격에 대한 민감도 차이가 있었으며, Claude-3-Haiku가 가장 덜 민감했지만 ASR은 여전히 70% 이상이었음

정상 도구가 9,650개인 ToolBench에 악성 도구 문서 하나만 주입해도 기울기 비사용 방법은 96.1%, 기울기 기반 방법은 97.8%의 AHR을 달성함

- (그림3)
    
    기울기 비사용 방법과 기울기 기반 방법 모두 10개의 서로 다른 작업에서 전반적으로 높은 AHR과 ASR을 보임
    
    MetaTool에서는 공격 성능이 비교적 높고 일정하게 유지되며, ToolBench에서는 AHR은 높지만 ASR이 작업에 따라 다소 차이를 보임
    
    이를 통해 ToolHijacker가 특정 작업에만 한정되지 않고 다양한 작업에서 효과적임을 보여 줌
    

ToolHijacker는 기존 수동 공격, JudgeDeceiver, PoisonedRAG보다 높은 공격 성공률을 보임

기존 공격은 검색 단계까지 충분히 고려하지 못하지만, ToolHijacker는 여러 작업 설명에 대해 검색과 선택을 함께 최적화하기 때문에 더 높은 성능을 보임

ToolHijacker가 생성한 악성 도구 문서는 비교적 짧아 문서 길이만으로는 정상 도구 문서와 구별하기 어려움

- (그림4)
    
    정상 도구 문서의 토큰 길이는 데이터셋에 따라 매우 다양하며, 특히 ToolBench에서 큰 차이를 보임
    
    ToolHijacker의 기울기 비사용 및 기울기 기반 방법으로 생성한 악성 도구 문서는 비교적 짧고 정상 도구 문서의 길이 범위 안에 포함됨
    
    따라서 문서의 토큰 길이만으로는 ToolHijacker가 생성한 악성 도구 문서와 정상 도구 문서를 구별하기 어려움
    

C) 절제 실험

검색기의 영향: 4개 검색기 모두에서 높은 성능을 유지함. 기울기 비사용 방법은 평균 AHR 100%, ASR 99%를 기록했고, 기울기 기반 방법도 평균 AHR 100%, ASR 98.75%를 기록함

k의 영향: 검색 후보 수 k가 작으면 악성 도구가 검색되지 않을 가능성이 커져 성능이 감소함. k가 3보다 커지면 AHR과 ASR이 높은 수준으로 안정화됨

- (그림 5)
    
    표적 검색기의 후보 수 k가 증가하면 악성 도구가 검색 결과에 포함될 가능성이 높아져 AHR이 빠르게 100%에 가까워짐
    
    대리 검색기의 후보 수 k′가 2나 3처럼 작으면 ASR이 불안정하며, 특히 기울기 기반 방법에서 성능이 크게 감소함
    
    k′가 5 이상이면 기울기 비사용과 기울기 기반 방법 모두 AHR과 ASR이 높은 수준으로 안정화됨
    
    따라서 대리 환경에서 충분한 수의 도구 후보를 사용해야 다양한 표적 검색 설정에서도 안정적인 공격 성능을 얻을 수 있음
    

k′의 영향: 대리 환경의 후보 수 k′가 너무 작으면 S가 충분히 최적화되지 않아 ASR이 불안정해짐. k′가 5 이상이면 공격 성능이 높아지고 안정적으로 유지됨

대리 작업 설명 수의 영향: 대리 작업 설명 수 m′는 AHR에는 큰 영향을 주지 않았지만, 개수가 증가할수록 ASR이 향상됨. 특히 기울기 기반 방법은 작업 설명이 1개일 때 ASR 32%에서 7개일 때 98%로 증가함

- (그림6)
    
    대리 작업 설명 수 m′가 달라져도 두 방법의 AHR은 모두 100%로 유지되어 검색 성능에는 큰 영향을 주지 않음
    
    기울기 비사용 방법은 대리 작업 설명이 1개일 때도 높은 ASR을 보이며, 3개 이상에서는 거의 100%로 안정화됨
    
    기울기 기반 방법은 대리 작업 설명이 1개일 때 ASR이 약 32%로 낮지만, 설명 수가 증가할수록 크게 향상되어 7개일 때 약 98%를 기록함
    
    따라서 다양한 대리 작업 설명을 사용할수록 특히 기울기 기반 방법의 선택 성능이 향상됨
    

R과 S의 영향: R은 악성 도구를 검색 후보에 포함시키는 데 중요하고, S는 악성 도구가 최종 선택되도록 하는 데 중요함. R만 사용하면 검색은 되지만 최종 선택 성공률이 매우 낮아져 두 부분을 함께 사용해야 높은 성능을 얻을 수 있음

대리 LLM의 영향: 성능이 좋은 대리 LLM을 사용할수록 ASR이 높아짐. 기울기 비사용 방법은 대리 LLM이 달라져도 비교적 안정적이지만, 기울기 기반 방법은 대리 LLM의 성능에 더 큰 영향을 받음

유사도 지표의 영향: 코사인 유사도와 내적 모두 AHR 100%를 기록하여 유사도 계산 방식은 검색 성공률에 큰 영향을 주지 않음. 내적을 사용했을 때 기울기 기반 방법의 ASR이 소폭 향상됨

악성 도구 수의 영향: 대리 환경의 정보가 부족한 경우 악성 도구 문서를 여러 개 주입하면 공격 성능이 높아짐. 여러 문서가 같은 악성 도구의 선택을 유도하도록 설정했을 때 AHR과 ASR이 거의 100%로 유지됨

- (그림7)
    
    악성 도구 문서를 1개만 주입했을 때보다 2개를 주입했을 때 전반적으로 ASR이 향상됨
    
    각 악성 문서가 자신을 선택하도록 하는 개별 설정은 기울기 비사용 방법에서 높은 성능을 보이지만, 기울기 기반 방법은 k가 증가하면 ASR이 다소 감소함
    
    여러 악성 문서가 동일한 도구의 선택을 유도하는 통합 설정에서는 두 방법 모두 AHR과 ASR이 거의 100%로 유지됨
    
    따라서 악성 도구 문서의 수를 늘리고 동일한 도구를 선택하도록 구성하면 공격 효과가 크게 강화됨
    

**V. 방어**

프롬프트 주입 방어는 공격 자체의 영향을 줄이는 예방 기반 방어와 악성 문서를 찾아내는 탐지 기반 방어로 구분함

예방 기반 방어로 StruQ와 SecAlign을 평가하고, 탐지 기반 방어로 알려진 정답 탐지, DataSentinel, PPL, PPL-W를 평가함

A) 예방 기반 방어

StruQ: 안전한 지시와 사용자 데이터를 분리하고, 데이터 안의 지시는 무시하도록 LLM을 학습함

SecAlign: 프롬프트가 주입된 상황에서도 안전한 출력을 우선하도록 LLM을 학습함

두 방어가 적용된 LLM에서도 ToolHijacker는 84.6%~99.6%의 높은 ASR을 기록하여 공격을 충분히 막지 못함

SecAlign이 StruQ보다 ASR을 더 많이 감소시켜 상대적으로 방어 성능이 높았지만, 여전히 대부분의 공격이 성공함

ToolHijacker의 악성 도구 설명은 명백하거나 작업과 무관한 지시를 포함하지 않고, 정상적인 도구 기능 설명처럼 의미적 일관성을 유지하기 때문에 기존 예방 방어를 우회함

ToolBench에서는 MetaTool보다 ASR이 다소 낮았으며, 이는 ToolBench의 도구 라이브러리 규모가 더 크기 때문일 가능성이 있음

ACC-a와 ASR의 합이 100%가 되지 않는 경우는 LLM이 유효한 도구를 선택하지 못하거나 요청을 거부했기 때문임

- (그림8)
    
    StruQ와 SecAlign 모두 ToolHijacker의 ASR을 어느 정도 감소시키지만, 감소 폭은 크지 않음
    
    SecAlign이 StruQ보다 ASR을 더 많이 낮추며, 특히 ToolBench의 기울기 기반 공격에서 가장 큰 감소 효과를 보임
    
    전반적으로 기울기 기반 공격과 ToolBench 환경에서 방어 효과가 더 크게 나타남
    
    그러나 최대 감소 폭도 약 10%에 불과하므로 두 방어 방법 모두 ToolHijacker를 충분히 막지는 못함
    

B) 탐지 기반 방어

알려진 정답 탐지: 문서와 함께 특정 문구를 출력하라는 지시를 제공하고, LLM이 해당 문구를 출력하지 못하면 문서에 악성 지시가 포함된 것으로 판단함

DataSentinel: 알려진 정답 탐지를 발전시켜, 미세 조정된 탐지 LLM으로 프롬프트 주입을 식별함

PPL 탐지: 문장의 퍼플렉서티가 임계값을 넘으ㅊ면 의미적 일관성이 깨진 악성 문서로 판단함

PPL-W 탐지: 문서 전체가 아닌 일정한 크기의 구간별로 퍼플렉서티를 계산하여 비정상적인 부분을 탐지함

탐지 성능은 악성 문서를 정상으로 놓친 비율인 FNR과 정상 문서를 악성으로 잘못 분류한 비율인 FPR로 평가함

알려진 정답 탐지는 모든 공격에서 FNR 100%를 기록하여 악성 도구 문서를 전혀 탐지하지 못함

DataSentinel도 FNR 90%~100%를 기록하여 대부분의 악성 도구 문서를 놓침

PPL과 PPL-W는 기울기 기반 공격의 일부를 탐지했지만, 전체적으로는 악성 문서의 대부분을 식별하지 못함

기울기 기반 문서는 토큰 단위로 최적화되어 문장이 다소 부자연스러워질 수 있으므로 기울기 비사용 문서보다 퍼플렉서티 탐지에 더 잘 걸림

기울기 비사용 문서는 문장 수준의 자연스러움과 의미적 일관성을 유지하여 대부분의 탐지 방법에서 FNR 100%를 기록함

방어 실험 결론

기존 예방 기반 방어는 ToolHijacker의 공격 성공률을 충분히 낮추지 못했고, 탐지 기반 방어도 악성 도구 문서 대부분을 놓침

이는 ToolHijacker가 명백한 공격 지시를 삽입하는 대신 표적 작업과 의미적으로 자연스럽게 연결되는 도구 설명을 생성하기 때문임

**VI. 관련 연구**

A) LLM 에이전트의 도구 선택

기존 연구는 LLM이 외부 API와 전문 도구를 사용할 수 있도록 연결하고, 작업에 적합한 도구를 정확하게 선택하도록 성능을 높이는 데 집중함

TaskMatrix.AI, Gorilla, REST-GPT 등의 시스템은 LLM과 다양한 API를 연결했으며, ToolBench와 MetaTool은 도구 사용 및 선택 능력을 학습하고 평가하기 위한 벤치마크를 제공함

최근에는 검색 반복, 다단계 학습, 재순위화, 그래프 기반 검색, 실행 피드백 등을 활용하여 도구 선택의 정확도와 안정성을 향상하는 연구가 이루어짐

그러나 이러한 연구는 대부분 도구 선택 능력을 높이는 데 집중했으며, 악성 도구 문서가 검색과 선택 과정에 미치는 보안 위험은 충분히 다루지 않음

B) 프롬프트 주입 공격

기존 프롬프트 주입 공격은 수동 공격과 최적화 기반 공격으로 구분됨

수동 공격은 단순 지시, 이스케이프 문자, 맥락 무시, 가짜 완료 등의 프롬프트를 사람이 작성하는 방식으로 직관적이지만 효과가 제한적이고 작성에 시간이 필요함

최적화 기반 공격은 이러한 한계를 보완하기 위해 공격 문구를 자동으로 개선하며, 기존 연구는 LLM 평가 조작, 시스템 프롬프트 추출, 미세 조정 데이터 오염 등을 대상으로 함

최근에는 도구 호출, 웹 에이전트, 다중 모달 및 다중 에이전트 환경에서의 프롬프트 주입 공격도 연구되고 있음

그러나 기존 연구는 주로 LLM의 응답이나 에이전트의 행동을 직접 조작하는 데 집중했으며, ToolHijacker는 에이전트의 핵심 의사결정 과정인 도구의 검색과 최종 선택을 공격한다는 점에서 차이가 있음

C) 방어

예방 기반 방어: 외부 데이터와 지시를 구분하거나, 원래 지시를 다시 강조하는 프롬프트 구조를 사용하여 주입된 지시의 영향을 줄임

StruQ와 SecAlign처럼 적대적 학습과 미세 조정을 통해 LLM의 프롬프트 주입 저항성을 높이는 방법도 제안됨

기존 보안 정책 기반 방어는 사전에 승인된 도구만 사용하게 하지만, 사용할 도구 집합이 이미 선택되었다고 가정하므로 도구 선택 과정 자체를 공격하는 ToolHijacker를 충분히 다루지 못함

탐지 기반 방어: 입력 문장의 퍼플렉서티나 알려진 작업의 수행 여부를 확인하여 악성 지시가 포함되었는지 탐지함

퍼플렉서티 탐지는 적절한 임계값을 정하기 어렵고 정상 문서를 악성으로 잘못 판단할 수 있으며, 알려진 정답 탐지와 DataSentinel도 의미적으로 자연스럽게 작성된 악성 도구 문서를 놓칠 수 있음

**VII. 결론 및 향후 연구**

LLM 에이전트의 도구 선택 과정이 프롬프트 주입 공격에 취약함을 확인함

악성 도구 문서를 자동으로 생성하여 도구의 검색과 최종 선택을 조작하는 ToolHijacker를 제안함

실험 결과 ToolHijacker는 기존 프롬프트 주입 공격보다 높은 성능을 보였으며, 예방 및 탐지 기반 방어도 공격을 충분히 막지 못함

PPL-W는 기울기 기반 악성 문서의 일부를 탐지했지만 여전히 상당수를 놓침

향후 연구로 도구 선택과 도구 호출을 함께 공격하는 방식의 분석과 ToolHijacker를 막기 위한 새로운 방어 전략 개발을 제시함

윤리적 고려 사항

모든 실험은 실제 사용자와 시스템에 피해를 주지 않는 통제된 로컬 환경에서 진행함

악성 도구 문서를 실제 온라인 플랫폼에 배포하거나 실제 악성 도구를 개발하지 않음

코드와 데이터는 사용 목적과 허가를 확인한 뒤 제한적으로 공개할 예정임

OpenAI, Anthropic, LangChain 등 관련 기업에 연구 결과와 취약점을 알렸지만 아직 답변을 받지 못함

취약점 공개가 더 엄격한 도구 검증과 안전한 LLM 에이전트 설계에 도움이 되므로 공개의 이익이 위험보다 크다고 판단함

사용자 연구 참가자에게 연구 목적을 설명하고 동의를 받았으며, 연구에 필요하지 않은 개인정보는 수집하지 않음
